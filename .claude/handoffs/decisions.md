# Decisions made during the build

Format: date · who · decision · why. Newest first.

- 2026-10-10 · Fiqri · Client-event notifications fall back to all active Lawyers whenever no active recipient remains (not only when the client has no cases) · A client message must never go unseen.
- 2026-10-10 · developer (M7 review fix) · The notifications list pages 50 at a time (`?p=N`, Load older / Newer) instead of a fixed latest-100 cap. Firm recipients are active users only. Post-commit notify failures are logged and swallowed (`AfterCommitAsync`) · Review Should fix 1 and 3.
- 2026-10-10 · developer (M7) · Notify is called inside the services right after their commit (where the M3..M6 markers were), not in page handlers. Chat uses two kinds: `ClientMessage` (firm recipients, in-system) and `FirmMessage` (client, in-system + email). Notification titles are stored resolved in the recipient's language at creation and carry a context (case title, client name or bill number; in-system only, never in email); a later language switch does not re-translate old rows. Client emails say only what happened plus `APP_BASE_URL/Account/Login?ReturnUrl=<target path>` (R-099). Inactive Client users still get the in-system row but no email (Q-18). Opening a notification is a POST form per item (marks read, redirects); GET is 404. Firm uploads notify nobody (R-090 is client uploads only). Send test email (R-113) not built (cut) · Simplest readings.
- 2026-10-10 · developer (M6) · Bills: line amounts must be above RM 0.00 and are rounded to 2 decimals half away from zero when set; the total is the exact sum of the rounded lines (numeric(12,2) max 9,999,999,999.99). Bill number year = creation date in Asia/Kuala_Lumpur. Edits on a Sent/Paid bill return 400. Line rows are deleted when removed from a Draft (lines are not records to keep; bills themselves are never deleted, Q-07). Client bill page shows "Amount due" for Sent, "Amount paid" + paid date for Paid. Settings: a blank SMTP password keeps the stored one (checkbox to remove it); a Lawyer cannot deactivate their own account; client logins are not managed on Settings (404). The QR image is shown through a 5-minute presigned URL; replacing it keeps the old object. Staff/Bills and Portal/Bills lists built (Q-04, cut item 4 not applied) · Simplest readings.
- 2026-10-10 · developer (M5, revised after review) · Chat: messages and captions are 1..4000 characters after trimming (a caption may be empty). A file message carries the composer text as its caption (R-067 "text and/or a file"). Chat file uploads and downloads are audited as `Message.FileUploaded` / `Message.FileDownloaded` (entity `Message`); download is `/Files/Download/{messageId}?handler=Message`. The poll cursor is `messages.seq` (identity); inserts into one chat are serialised by a per-client advisory transaction lock so seq order is commit order. Read state (Q-05): opening the chat, or a poll while the page is visible, marks the other side's messages read, only up to the highest seq shown to that viewer; background-tab polls do not mark read. Bubble sides mirror the viewer: firm messages on the right for firm users, the client's on the right in the portal ("same bubbles" read as same style). The sidebar Chats pill and the dashboard tile count chats with unread client messages; the portal counts unread firm messages · Review Critical 1, Should fix 1-3, Nice 5; R-067..R-069, R-074, R-136.
- 2026-10-10 · developer (M4 review fix) · Uploads go through staging: the presigned PUT targets an unguessable `staging/<uuid>/<uuid>` key; completion validates it, copies it server side to the final case key, validates the copy, writes the row and deletes the staging object. Staging objects are not documents, so deleting them does not break "nothing is deleted" (R-114); leftovers (abandoned or refused uploads) are expired by an R2 lifecycle rule on `staging/` after 1 day (deployer). The PUT is not bound to Content-Length; the size limit is enforced on the final copy · Review Critical 1 and Should fix 2; works on R2 and SeaweedFS without If-None-Match.
- 2026-10-10 · developer (M4 test fix) · The portal case page shows Received requests read only (status pill, no upload) under "Documents you have sent"; Home's "We still need from you" keeps only Pending and Rejected · Done-criterion "request shows Received in both areas".
- 2026-10-10 · developer (M4) · Uploads: the content type is taken from the file extension (pdf/docx/jpg/jpeg/png) and signed into the presigned PUT; completion rejects a stored type that differs or is not allowed, or a size over 20 MB or 0, and deletes the object. Upload tickets live 15 minutes (PUT URL 10 minutes) so a slow upload can still complete. Completing the same ticket twice returns the first document. A refused completion for access reasons (404) leaves the object in place · R-054, R-055, R-057, R-114.
- 2026-10-10 · developer (M4) · Only Clients upload against a request (Pending or Rejected, on their own case); firm users upload plain case documents and a firm upload carrying a request id is 404. Only Received requests can be rejected (a Pending one has no file); the rejection reason is kept on the request after a re-upload but shown only while Rejected · R-046..R-049, Q-11, Q-12.
- 2026-10-10 · developer (M4) · Upload errors: access failures are 404; type, size, missing object and expired/tampered ticket are 400 with a localised message shown under the picker. After a successful upload the page reloads (no HTMX swap) · Simplest reading.
- 2026-10-10 · Fiqri · Only Lawyer/OM can change a client's email (login); overrides the Q-14 default · Prevents Staff taking over a client account via email change + Forgot password.
- 2026-10-10 · developer (M3 review fix) · Changing a client's login email rotates the security stamp, so set-password/reset links sent to the old address stop working (open sessions end too). If the login has no password yet, a fresh account-created link goes to the new address. If an account-created email fails, the client is still saved and the creator sees a warning to use Forgot password · Review Critical 1 and Should fix 2.
- 2026-10-10 · developer (M3) · Staff Past cases live at `/Staff/PastCases` (`Pages/Staff/PastCases.cshtml`, matching the M2 sidebar link) instead of `Pages/Staff/Cases/Past`; the portal one is `/Portal/Cases/Past` as planned · Keeps sidebar highlighting correct without touching the layout.
- 2026-10-10 · developer (M3) · Chat links on the Client and Case pages point to `/Staff/Chats/{clientId}`; M5 must serve that route. Portal Home "Upload" buttons link to the case page until M4 wires uploads · Avoids dead routes changing later.
- 2026-10-10 · developer (M3) · Dashboard tiles: "documents pending" = Pending + Rejected requests (Q-03); "unread chats" = clients (that the user can open) with at least one unread message sent by the client's own login; "bills awaiting payment" = Sent bills. All counted in SQL over `CasesFor`/`ClientsFor` · Simplest reading of R-137.
- 2026-10-10 · developer (M3) · Q-10 enforcement: the case Edit page saves title/type/description for anyone who can open the case; lawyer in charge and assigned staff are read only for Lawyer/OM. - 2026-10-10 · developer (M3), Completed↔Cancelled rule confirmed by Fiqri 2026-10-10 · Status changes: any status to any status; entering Completed/Cancelled sets `closed_at`, Completed↔Cancelled keeps the first `closed_at`, any active step clears it. - 2026-10-10 · developer (M3) · Clients list chip "All" includes deactivated logins; "Inactive" shows only deactivated ones. - 2026-10-10 · developer (M3) · Tests for Lawyer/OM pages use `FirmAppFactory` (REQUIRE_FIRM_2FA=false); `AppFactory` keeps the production default for the 2FA tests · No TOTP plumbing in tests.

- 2026-10-10 · developer (M2 review fix) · Email links are built only from `APP_BASE_URL` through `IAppLinks` (`Infrastructure/AppLinks.cs`, `SetPassword(userId, token)`), never from the request Host. Production refuses to start without `APP_BASE_URL`; other environments fall back to http://localhost:5000. `AllowedHosts` from config wins; in Production it defaults to the `APP_BASE_URL` host · Prevents password-reset poisoning. Deployer: set `APP_BASE_URL` per Vercel environment (preview URLs need their own value or an `AllowedHosts` override).
- 2026-10-10 · developer (M2 review fix) · Sessions of deactivated users end at the next security-stamp check: interval 60 s (`SECURITY_STAMP_INTERVAL_SECONDS`, tests use 0), the stamp check also rejects `is_active = false`, and deactivation goes only through `UserManager.DeactivateAsync` (clears the flag and rotates the stamp) · Deactivation must take effect promptly.
- 2026-10-10 · developer (M2) · The role has one source of truth: the `users.role` column (TSD). Identity role tables (`roles`, `user_roles`, `role_claims`) are dropped; `AppDbContext` is an `IdentityUserContext`, and `AppClaimsPrincipalFactory` issues `users.role` as the role claim (plus display name, language, 2FA state). Folder policies and `IAccessService` read that claim · Two role stores drift; the TSD names the column. Role changes reach existing sessions at the next security-stamp check (30 min) or immediately if the stamp is updated.
- 2026-10-10 · developer (M2, revised after review) · Only 404 responses (missing rows, access failures, unknown URLs) and 403s (re-mapped to 404, and the cookie `OnRedirectToAccessDenied` sets 404) re-execute `/NotFound`. 400, 405 and 500 keep their own status. An anonymous visitor who fails a policy is redirected to Login · R-008/R-156 apply only to access failures; an expired antiforgery token is not "page not found".
- 2026-10-10 · developer (M2) · Auth and culture cookies are `Secure` always (R-027). Browsers accept Secure cookies on http://localhost (Chrome, Firefox); tests use https://localhost. Vercel TLS is honoured through forwarded headers · Same cookie settings in dev and prod.
- 2026-10-10 · developer (M2) · Language: a signed-in user's culture comes from `users.language` (claim); visitors use the culture cookie; default `en`. The EN|BM switch (`/Account/Culture`) sets the cookie and, when signed in, also saves `users.language` · R-105, R-106.
- 2026-10-10 · developer (M2) · The 2FA login page accepts a 6-digit authenticator code or a recovery code in the same field. Lawyer and Office Manager cannot turn 2FA off; Staff and Client can (R-024) · Fewest screens.
- 2026-10-10 · developer (M2) · Failed logins for unknown emails are audited with `user_id` null and the typed email in `details` (Q-19) · PDPA access log needs attempted logins.
- 2026-10-10 · developer (M2, revised after review) · SMTP uses MailKit as the TSD specifies: port 465 = implicit TLS, 587 = STARTTLS required, other ports = STARTTLS when offered; 5 s timeout. Password protector purpose `ClientHub.SmtpPassword` (`SmtpEmailSender.ProtectorPurpose`) for M6. With no SMTP host the email is logged in full only in Development; elsewhere only subject and masked recipient (bodies carry set-password tokens) · Follows the TSD stack; supports both common SMTP ports.
- 2026-10-10 · developer (M2) · `_Input` partial takes a field name and value (not a `ModelExpression`) and reads errors from ModelState; component styles are CSS classes in `wwwroot/css/input.css` (`btn-*`, `badge`, `input`, `card`) used by the partials.
